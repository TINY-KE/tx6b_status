# 部门人员在位看板（微信小程序 + 云开发）

把「谁现在在哪」变成一眼能看清的一张看板。需要外出的人填一下去哪、什么时候（京内出差 / 京外出差 / 请假），
同事想找人的时候打开小程序搜一下就知道。

> **「在办公室」不需要填**——它是默认状态，没填的人一律显示为在岗。这样填写成本最低，
> 也避免「为了显示在岗反而要每天报一次到」的反直觉负担。

## 功能

- **在位看板**（首页）
  - 屏幕一：今天的在位时间轴。横轴 8:30 – 18:00，每 30 分钟一个点，外出用对应颜色标出，一眼看出谁什么时候在哪。
    这一屏的顶部（页签正下方）有一行四项统计（在岗 / 京内出差 / 京外出差 / 请假）。
    **它只统计今天，所以只挂在今天这一屏**，切到右边三屏就跟着滑走——那三屏的列头可没有「今天的人数」。
  - 屏幕二：未来 3 个工作日，**今天排最左**，往右依次是明天、后天（例：9/14 周一 · 9/15 周二 · 9/16 周三）。
    列头里今天那一列会加粗变蓝，避免看错列。
    每天一条色条，**条内再按时间段分段着色**（左端 8:30、右端 18:00）：
    比如上午京外出差、下午没安排，色条就是「左半段红 + 右半段绿」，而不是整条一个颜色。
    色条正下方列出当天**所有不在岗时段**的备注 + 时间段（例：「病假 08:30-12:00」），
    一天有多段就列多行；全在岗的那天不出文字，行高不变。
  - 屏幕三：未来 7 个工作日。与屏幕二同一种色条画法，但 7 列更窄——
    列头拆成「日期 + 星期」两行、字号缩小，色条下的备注不再显示（点色条看弹窗）。
  - 屏幕四：未来一个月（30 个自然日）。每天一格的色块条：
    有不在岗记录的日期按状态着色（绿/黄/红/灰，**与色条同一套色值**），
    没有记录的周末/节假日画成**空心格**（不填色只留描边），工作日填绿；
    调休上班的周末按工作日显示。点色块同样弹出该人「今天及以后的全部不在岗申请」。
  - 四屏左右滑动切换，顶部按钮按科室筛选。
- **填写去向**：选去向 → 选「开始时间（日期 + 时刻）→ 结束时间（日期 + 时刻）」。
  页面顶部有一条说明栏：**在岗是默认状态，不用填写**（左侧绿方块对应看板上的在岗绿条），
  没有登记的时段看板一律按在岗显示。
  出差跨天时把两端日期选成不同天即可，最长 30 天。
  卡片底部有快捷选项（今天上午 / 今天下午 / 今天整天 / 今天起连续 N 天 / 明天起连续 N 天），
  点一下连日期和时刻一起填好。
  备注栏里，请假事由**只能**从 7 个固定选项点选（事假 / 病假 / 年休假 / 探亲假 / 婚假 / 产假 / 丧假），
  请假时不出现输入框；出差地仍是打字 + 历史点选。
  **备注卡在没选去向时整块不显示**——备注的含义取决于去向（出差地 / 请假事由），
  先选去向，标题才有意义。
- **身份认领**：管理员导入部门名册后，每个人进来自选自己的名字，
  **填上工号核对身份**（工号必须与名册里登记的一致，否则认领失败），不会有重名混乱。
- **名册管理**（管理员）：批量粘贴导入（姓名 / 工号 / 科室三列）、单人增删、
  逐人补填或修改工号、设置管理员。
- **考勤表导出**（管理员，管理页第三个页签）：选月份 → 点「生成考勤表」→ 再点「转发到微信」。
  **刻意分成两次点击**（原因见下文「转发为什么必须单独一次点击」），不是偷懒少写一步。
  列：序号 · 工号 · 姓名 · 出勤 · 年休假 · 探亲假 · 婚假 · 产假 · 丧假 · 事假 · 病假 · 小计。
  口径见下文「导出考勤表的口径」。
- **默认在岗**：没填的人一律按在岗显示（绿点），不区分「填的」和「没填的」——
  既然在岗无需填报，两者没有区别。未填状态不写进数据库，只在查询时补上。
- **看板标签显示备注**：人员行右侧标签优先显示「出差地 / 请假事由」+ 时段（例：「市发改委 08:30-18:00」），
  没有备注时才显示「京内 / 京外 / 请假」。超长自动截断，避免撑破列表。
- **点姓名拨打电话**：看板两屏里点任意同事的姓名 → 确认框「确定要给 XXX 拨打电话吗？」→ 直接调起拨号。
  号码就是本人认领时自己填的那个（`presence` 云函数从 `staff` 记录带出 `phone`）。
  未认领、或已认领但没填电话的人，会分别给出对应提示，不会静默无反应。
- **状态配色**：在岗 = 绿 · 京内出差 = 黄 · 京外出差 = 红 · 请假 = 灰。
  配色写死在页面样式里（5 组类名：`.st-` 统计数字 / `.d-` 点阵与图例 / `.tag-` 状态标签
  / `.bar-` 3 天·7 天色条 / `.mc-` 一个月视图色块），
  改色要同步 `app.wxss` 的 `--st-*`、`utils/status.js` 的 `TYPES` 与这两个页面的 wxss。
- **京内是双色调，别合并**：点阵 / 色条 / 选中按钮底用亮黄 `#ffc107`（小色块，越亮越看得出是黄色）；
  统计数字等文字用金 `#c08a00`——亮黄当文字压白底只有 1.6:1 完全读不了，
  `#c08a00` 是白底上还能读的最亮的黄（3.05:1）。

## 部署步骤

### 1. 注册小程序并开通云开发

到 [mp.weixin.qq.com](https://mp.weixin.qq.com) 注册一个小程序，拿到 AppID。
用微信开发者工具导入本项目根目录，在 `project.config.json` 里把 `appid` 换取你自己的。
点击工具栏「云开发」，按提示开通，记下**环境 ID**。

### 2. 环境 ID

`miniprogram/app.js` 第一行已填入本项目的环境 ID：

```js
const CLOUD_ENV_ID = 'cloud1-d7g87r7wxb0945808';
```

换到别的云环境时改这一行即可。

> 未填写时**会退回默认环境**而不是报错，AppID 下只有一个环境时同样能正常运行。
> 但一旦你建了第二个环境，就必须填明确的环境 ID，否则会连到错误的环境。

### 3. 数据库集合（无需手动创建）

两个集合会在**云函数首次调用时自动创建**，不需要去控制台手工新建：

| 集合名 | 用途 |
|---|---|
| `staff` | 部门名册（每个人的姓名、工号、科室、认领状态） |
| `presence` | 去向记录（谁、什么状态、什么时间段） |

自动创建由三个云函数里的 `ensureCollections()` 完成。若你的环境限制了该 API，
也可以在云开发控制台 → 数据库里手工新建，效果完全相同。

**权限设置（建议确认一次）**：两个集合都设为「仅管理端可读写」（即所有用户不可读写）。
本项目的所有数据读写都走云函数，云函数拥有管理端权限，不受该设置影响，
这样能避免用户绕过云函数直接读写数据库。

### 4. 部署云函数

在开发者工具左侧文件树中，分别右键 `cloudfunctions/` 下的三个目录上传部署：

- `cloudfunctions/login`
- `cloudfunctions/presence`
- `cloudfunctions/staff`

三个都要部署，缺一不可。三个函数**都没有第三方依赖**（只用云函数环境自带的
`wx-server-sdk`，以及 `presence` 生成 xlsx 用的 node 内置 `zlib`），
所以「上传并部署：云端安装依赖」和「上传并部署：所有文件」都可以，不会因为漏装依赖出问题。

### 5. 创建第一个身份并导入名册

编译运行小程序，用你自己的微信进入「我的」。

此时名册还是空的，页面会显示「**创建第一个身份**」：

1. 填上你的姓名、工号、选好科室和电话，点「创建并成为管理员」→ 你自动成为管理员。
2. 进入「名册管理」→「批量导入」，把部门名册（**姓名 / 工号 / 科室**三列）粘贴进去。
3. 把小程序码发到部门群里，其他人进「我的」填上工号认领自己的名字即可。

> 如果名册里已经有内容（比如你手工在控制台导了数据），
> 那么**第一个认领的人会同样自动成为管理员**，
> 之后可以在「名册管理」里给其他人授权管理员。

名册每行一个人，**需要「姓名 + 工号 + 科室」三列**，可以直接从 Excel 复制粘贴：

```
张三,10086,1室
李四,20099,2室
王五,30011,3室
赵六,40022,部办
```

- **列的顺序随意**，程序按「列的角色」认，不按位置：`张三,10086,1室`、
  `10086,张三,1室`、`张三,1室,10086`、甚至制表符 / 空格分隔都能识别。
  这么设计是因为从 Excel 复制过来的列序五花八门，按位置硬编码会在某一行静默错位
  （把工号当姓名导进去，而且因为三列都"有值"不会报错，等人认领不上才发现）。
- 科室会自动归一化，「一室」「1 室」「办公室」都能识别成 `1室` / `部办`。
- **工号必填**，缺工号（或工号不是"数字字母"形态）的行不会导入，
  粘贴后预览里会提示「另有 N 行缺少工号或格式不对」。
- 工号会统一成大写、去掉空格与 `-` `_`，所以名册里存 `A100`、本人打 `a-100` 也能认领成功。
- **管理员不导入电话**——电话是个人资料，由各人认领时自己填。
  多余列（比如从别的表里带过来的电话列）会被忽略。

### 6. 通知同事

把小程序码发到部门群里即可。每人进来填上自己的工号、认领自己的名字就能用，
不会认错人（同名的人会带上科室区分，工号更是唯一的）。

认领时名册列表上方有两个必填栏：**工号**和**电话**。

**工号由管理员导入，本人只填一遍做核对**：

- 填的工号必须与名册里登记的**一致**才能认领成功，不一致会提示「工号与名册记录不一致」
- 认领之后**不能自己改**——它是核对身份的凭据，让被核对的人自己改就等于把答案给了他。
  写错了找管理员，在「名册管理」里逐人可改（那一栏也会显示成不可编辑的灰色文字）
- 名册记录里**没有工号**的人会认领失败，提示「请联系管理员补填」；
  管理员在名册列表里会看到这个人挂着琥珀色的「缺工号」小标，点「补工号」填上即可
  （存量名册是早先用两列格式导的，都没有工号，需要这样补一遍）

**电话号码由本人自己填写，不经管理员之手，而且是必填的**：

- 认领身份时，在名册列表上方填「电话」，点自己名字时一并保存（没填会被拦下）
- 认领之后随时可以在**「我的 → 编辑我的资料」**里修改（也不允许清空）
- 名册为空时走「创建第一个身份」的同事，同样要填

保存时会去掉空格、横线和括号（`010-12345678` → `01012345678`），
兼容手机号、座机和 4 位以上的分机短号（4–20 位数字）。

前端提交时拦一次，云函数 `claim` / `bootstrap` / `updateProfile` 三处也都拦一次——
只靠前端的话，旧版本客户端或直接调接口都能绕过去。

管理员在「名册管理」里能看到每个人填的电话与工号（电话只读，用于需要时联系；
工号可改，用于纠错），但不能改动电话。

## 几个关键设计

### 未认领身份的人也能看和填，只在提交时拦（小程序审核要求）

审核会检查「打开小程序能不能看到核心功能」。所以**任何页面都不能用
「你还没认领身份」把主体内容整块挡掉**：

- 看板页：`join-tip` 是一条可点的提示条，**看板本身照常完整渲染**
- 填写页：`join-bar` 同样是提示条，**去向 / 时间段 / 备注 / 保存按钮全部正常显示**，
  未认领的人可以尽情填，只在**点「保存」那一刻**弹出说明

拦在提交点用的 `wx.showModal` 而不是 `wx.showToast`——toast 只能报错，
modal 可以带一个「去认领」按钮直接把人送过去；另一个选项是「继续填写」，
`wx.switchTab` 会保留页面实例，**已经填好的内容不会丢**，认领完切回来接着提交就行。

关键实现就一条：**wxml 里不要有把表单包起来的 `wx:else`**。
原来正是 `<view class="join-card" wx:if="{{!joined}}">` + `<block wx:else>` 这个组合
把整个表单挡在了分支外面，改成条件渲染的提示条即可。

### 「第一个使用者自动成为管理员」的判断方式

认领时如果「还没有任何人认领过」，就把这个人设为管理员——名册为空时的第一个使用者
不用手工配置也能进管理页。这个判断写过两版：

```js
// ✗ 用「字段是否存在」推断「有没有人认领过」——不可靠
const claimedCount = await db.collection('staff')
  .where({ claimedAt: db.command.exists(true) }).count();
const isFirst = claimedCount.total === 0;

// ✓ 用 openid 口径（与项目里「未认领」的判定一致），再加一道保险
const claimedCount = await db.collection('staff').where({ openid: db.command.neq('') }).count();
const adminCount = await db.collection('staff').where({ isAdmin: true }).count();
const isFirst = claimedCount.total === 0 && adminCount.total === 0;
```

第一版的线上后果是：**每个新认领的人都拿到管理员标记**（`exists` 查询没有按预期筛出
「已认领」的记录，`claimedCount` 恒为 `0`，于是人人都判成"第一个"）。

第二版额外加了 `adminCount` 这道保险——**只要库里已经存在任何管理员，就绝不再自动授予**，
即便判断再次失效也不会继续扩大污染。云函数里还留了一行
`console.log('[claim] claimed=… admin=… isFirst=…')`，出问题时在云函数日志里一眼能看清。

已经写进库的错误标记，用「名册管理 → 修正管理员标记 → 只保留我为管理员」清一次
（对应 `staff` 云函数的 `fixAdmins`，处理时会跳过操作者本人，不会把自己也降级）。

### 工号是认领流程里唯一的凭据，所以有三条硬规矩

认领页列出的是「还没被认领的人」，只给姓名和科室——**姓名是公开的、科室是公开的，
光靠"点一下自己的名字"其实是谁都能点别人的名字**。工号就是为了把这一步从"点一下"
变成"需要凭据"：

1. **认领列表接口不下发工号。** `staff` 云函数的 `claimableList` 只回 `_id / name / dept`。
   这个接口谁都能调，把工号一起下发就等于把答案印在了题面上。
2. **本人不能改自己的工号。** `login` 云函数的 `updateProfile` 里没有 `jobNo` 这一项，
   「我的 → 编辑我的资料」也把工号渲染成不可编辑的灰色文字。
   允许被核对的人改核对答案，工号就白设了。写错了由管理员在名册管理里改。
3. **归一化后再比对。** 工号统一成「大写 + 去掉空格与 `-` `_`」再存、再比，
   这样名册里存 `A100`、本人打 `a-100` / `a 100` 都能认领成功——
   工号是印在工牌上让人抄的，抄写习惯的差异不该让他认领失败。

实现上有三份 `normalizeJobNo`（`utils/roster.js`、`login`、`staff`）——
云函数不能 require 小程序端代码，只能各存一份。**三处必须逐字一致**，
单测里有一条断言把三份源码去掉注释与空白后逐字比对，另一条拿一组输入跑三份比结果，
改规则时别忘了同步。

一个例外：名册里**一个管理员都没有**、而目标记录又没有工号时（例如在控制台手工灌了
名册数据、还没人认领过），认领会放行并以本人填的工号回填记录。否则谁都补不了工号，
认领会被永久卡死。他认领成功后就是管理员，这个口子随即关闭（`adminCount > 0` 就走不到了）。

### 底部导航是自绘的（原生 tabBar 字号改不了）

原生 `tabBar` 的文字大小由客户端固定，**没有任何 WXSS 能改它**（实测过，`app.json`
里也没有字号字段）。所以为了跟整体放大的字号一致，底部导航改成自绘：

- `app.json` 的 `tabBar` 加 `"custom": true`（`list` 仍要写全，框架靠它识别哪些是 tab 页）
- `miniprogram/custom-tab-bar/` 下四个文件，和 `pages` **同级、必须叫这个名字**，否则报
  `Component is not found in path "custom-tab-bar/index"`
- 三个 tab 页的 json 里都要有 `usingComponents` 字段（哪怕内容是 `{}`）
- 三个图标（在位看板 / 填写去向 / 我的）**用 WXSS 现画**，不加载任何图片文件，
  见 `custom-tab-bar/index.wxss` 里的 `.ico-board` / `.ico-fill` / `.ico-mine`

图标都是 `view` 拼出来的几何图形，未选中灰色（`#8a8a8e`）、选中品牌蓝（`#185fa5`）；
字号同步降到 28rpx（有图标后不需要那么大的字）。

三个坑：

1. **图标不要再改回 `<image>` + 图片文件。** 这个坑踩过两次：
   本地 `.svg` 在真机上不显示（开发者工具里显示正常，真机一片空白而且**不报错**）；
   换成 `.png` 之后**依然空白**，而路径、`packOptions.ignore`、样式、文件本身全都排查过没有问题。
   所以现在全部改成 WXSS 几何绘制（`view` + `border-radius` + `transform`），
   不依赖任何资源文件，开发者工具和真机表现一致。
   要改图标形状就改 `custom-tab-bar/index.wxss`；配色统一走 `currentColor`，
   所以选中态只需要 `.tab-item.on .tab-icon { color: #185fa5; }` 一行，
   不用再维护 normal / active 两套图。
   `assets/tabbar/` 下的 `.svg` / `.png` 和 `tools/make-tabbar-icons.py` 都已废弃，可以删。
2. **页面要自己留出底部高度。** 自绘 tabBar 是浮在页面之上的独立层，`100vh` 是整屏高度，
   不留白最后几行会被盖住。三个 tab 页都留了底部内边距
   （看板页 `104rpx`，填写页 / 我的页 `128rpx`），都写成 `calc(N + env(safe-area-inset-bottom))`。
   写法上先写一个不带 `env()` 的固定值兜底，再写带 `env()` 的那行覆盖——万一某机型不认
   `env()`，第一行还在，不会整条声明失效。
3. **每个 tab 页的 tabBar 是不同实例**，新实例的 `selected` 从 0 开始，等页面 `onShow`
   里 `setData` 才纠正，中间会闪一下选中项。所以组件自己在 `attached` 和
   `pageLifetimes.show` 里按 `getCurrentPages()` 的当前路径算一次选中项，页面还没画出来就是对的。
   页面上原有的 `this.getTabBar().setData({ selected: n })` 保留，两条路都通。

### 横向滚动的科室栏必须给死高度

科室按钮（`全部 / 1室 / 2室 …`）用横向 `scroll-view` 装，看板页和管理页各一处。
**`scroll-view` 的高度不能留 `auto`**：它内部那层滚动容器会把高度算错，药丸顶部被削掉一条——
真机上表现为上缘是平的、像被上方日期压住了，很容易误判成 z-index 或 margin 问题。

两处都改成「容器给死高度 + 药丸自己给死高度和 `line-height: 1`」：

| 位置 | 容器 `height` | 药丸 `height` |
|---|---|---|
| `pages/board/board.wxss` | 108rpx | 72rpx |
| `pages/manage/manage.wxss` | 100rpx | 60rpx |

药丸也用 flex 居中而不是靠 `padding` 撑高，且 `line-height: 1` 固定——这样以后再调字号，
行高变了容器高度不会跟着漂，不会又把药丸裁掉。

### 「区间视图」看的是「未来」，不是过去

看板主要给「提前安排」用——明天谁出差、下周谁请假，提前知道才好协调。
所以所有区间视图的列头都从**今天**开始往右排，周末打开时从下一个工作日算起。

三个区间视图的口径不同，别搞混：

| 视图 | 取列方式 | 渲染 | 云函数 |
|---|---|---|---|
| 3个工作日 | `nextWorkdays(3)`，跳节假日、算调休 | 色条 + 分段 + 备注 | `range` |
| 7个工作日 | `nextWorkdays(7)`，同上 | 色条（窄列，无备注，列头两行） | `range` |
| 一个月 | `nextDays(30)`，**自然日** | 每天一格色块，周末/节假日空心格 | `range` + `compact: true` |

两点连带事实：

- 未来日期没人填时按「默认在岗」显示成绿条，口径与当天一致，**不代表已经确认在岗**。
- 填写页本来就允许选未来 30 天（`FUTURE_DAYS = 30`），「连续 N 天出差」这类记录会自然落到未来那几列。

日期往后取用 `date.js` 的 `nextWorkdays()`（工作日）和 `nextDays()`（自然日）；
`recentWorkdays()` 是往前取的旧版本，看板已不用——名字相近，改的时候别拿错。

三个视图的数据在页面里各自独立存（`people3` / `people7` / `peopleM`），懒加载、互不覆盖；
切科室或下拉刷新会 `invalidateRanges()` 全部作废重拉。

**为什么一个月视图要 `compact` 模式**：30 天 × 每天若干段 if 回传完整的 19 格 segments，
响应会膨胀到几百 KB。compact 只回传每人一个 `marks` 数组（30 个格子各自的主导不在岗类型，
由云函数 `computeMarks()` 计算），加上 `applications` 弹窗数据，体积缩小一个数量级。

### 顶部四项统计只属于「今天」这一屏

在岗 / 京内出差 / 京外出差 / 请假 四个数字，口径就是**今天**——它们由 `loadToday()`
（`action: 'day'`）写入 `data.stats`，三个区间视图的 `loadRange()` 完全不碰它。

所以这四项**不能放在共用的 header 里**：3个工作日 / 7个工作日 / 一个月 页签下面若挂着
「今天的数字」，看着就像那三屏的人数统计。现在的做法是把它挂进**今天屏自己的
`swiper-item`**（`class="swiper-item today-screen"`）——切到别的屏时它跟着 swiper 一起滑走。

位置上有两点是刻意的：

- **在页签下方**（页签是 header 的最后一行，今天屏紧接其后）；
- **在 `scroll-view` 外面**：滚动名单时统计卡不动，理由和「图例固定在 header 不随列表滚动」一样。

⚠️ 改这一块时注意：`swiper-item` **不是 flex 容器**，统计卡下面直接放一个
`height: 100%` 的 `scroll-view`，两者会一起撑到屏幕外（名单整片看不见）。
必须靠 `.today-screen { display:flex; flex-direction:column }` 配
`.today-scroll { flex:1; height:0 }` 把名单区限制在剩余高度里。
`presence-today-stats-test.js` 有断言守着「stats 只在今天屏 / 不在 header / 在滚动区之外」
和这两条 flex 规则。

### 导出考勤表的口径

管理页第三个页签「考勤导出」。列固定为：
序号 · 工号 · 姓名 · 出勤 · 年休假 · 探亲假 · 婚假 · 产假 · 丧假 · 事假 · 病假 · 小计。

- **只统计工作日**，而且**日期由小程序端算好传给云函数**（`dateUtil.monthWorkdays(month, 今天)`）。
  云函数里没有节假日表——`holidays.js` 是唯一数据源，再存一份就是第四个副本，必然漏更新。
- **一天拆两个半天**：上午 08:30-12:00、下午 12:00-18:00，各记 0.5 天。
  记录与某个半天**只要有交集**，那个半天就按整半天算
  （10:00-11:00 的半天事假，也记 0.5 天事假）。
- **没登记的时段 = 默认在岗 = 出勤**，与看板「默认在岗」同一口径。
- **出差（京内 / 京外）计入出勤**，不单列一栏。
- **请假按事由归到对应列**；事由**不在 7 项白名单里的老记录忽略不计**，
  那半天落回默认在岗（白名单是后加的，早期记录里有「照料家人」这类自由文字）。
- **未认领身份的人不出现**（没有 openid 就没有归属），所以表里行数通常少于名册人数。
- **小计 = 出勤 + 各类假 = 该月工作日的天数**——这是恒等式，两边对不上就说明统计漏了数。
- 排序：科室升序，科室内按工号升序。只统计到**今天**，当月的未来工作日不进表。

**为什么出口只有「转发到微信」**：小程序没有通用的「保存到本地」接口
（`wx.saveFileToDisk` 只在 Windows / Mac 版微信可用），CSV 在手机上又打不开，
所以只能「真 .xlsx + `wx.shareFileMessage`」。文件放在云存储 `attendance/` 下、按月份命名，
**同一月份重复导出会覆盖上一次的文件**，不会越积越多。

#### 转发为什么必须单独一次点击

踩过的坑：原来是一个按钮「生成并转发」，真机上只弹一句**「转发未完成」**。真实原因是
`wx.shareFileMessage` **要求由用户点击手势直接触发**，而原流程是
「点击 → `await callFunction` → `await cloud.downloadFile` → 才转发」，
中间两段异步把手势上下文丢了，真机报
`shareFileMessage:fail can only be invoked by user TAP gesture`。
网上给的解法是「把生成和分享拆成两次点击，分享直接绑在按钮的 tap 上」，就按这个改了：

```
点「生成考勤表」 → 云函数生成 → 下载 → 落到本地带后缀的路径 → 出现「转发到微信」按钮
点「转发到微信」 → 处理函数里第一句就是 wx.shareFileMessage（无任何 await）
```

所以 `shareExport()` 里**不允许出现 `await`**，测试有一条断言守着（还给个负向验证：
塞一个 await 进去必须变红）。

另外一个必须做的事：**不要把 `downloadFile` 的 `tempFilePath` 直接拿去转发**。
那个临时路径没有后缀，微信和收到文件的人都按后缀判类型，分享出去会变成一个
「打不开的无名文件」。所以下载后先 `copyFileSync` 到
`wx.env.USER_DATA_PATH/考勤表-YYYY-MM.xlsx`（带后缀、同名覆盖、顺手清掉上一张），
转发用的是这个路径。`shareExport` 里因此看不到 `tempFilePath`。

非手机端（开发者工具、PC / Mac 版微信）这个接口会直接报 `not supported`，
所以先用 `wx.getDeviceInfo().platform` 判一下，不是 `android` / `ios` 就给一句
「请用手机扫码真机预览」，而不是让用户对着「转发未完成」猜。

**⚠️ 生成 xlsx 是手写的，零第三方依赖。** 原先用 exceljs，但云函数默认超时只有 3 秒，
而 exceljs 光冷启动 `require` 就要几百毫秒到 1 秒以上，加上生成与上传必然超时
（实测报的就是「生成失败」）。xlsx 的本质只是「一个 zip 容器 + 几个固定 XML」，
用 node 内置的 `zlib` 压一下就够，**生成只要几毫秒**。

代码在 `cloudfunctions/presence/index.js` 的「手写 xlsx」一节：`zipFiles()` 负责
把内存里的文件打成 zip（含自算的 CRC32 与 DOS 时间戳），`buildWorkbook()` 负责拼
`[Content_Types].xml` / `_rels/.rels` / `xl/workbook.xml` / `xl/worksheets/sheet1.xml` /
`xl/styles.xml` 这几个 XML。改表结构就改 `buildWorkbook` 里的 `headers` 与 `cell()`。

两个必须知道的约定（踩过才知道）：

- **`<worksheet>` 的子元素顺序是规定死的**：`sheetViews → sheetFormatPr → cols → sheetData`。
  调换顺序 Excel 会直接报「文件已损坏」，而这种错在开发者工具里完全看不出来。
- **`styles.xml` 里 `fills` 的前两项必须是 `none` 和 `gray125`**，这是 Excel 的硬约定，
  少一个文件会被判为损坏。

`presence-attendance-test.js` 里有 20 多条断言守着这些（包括真跑一遍生成器、
自己解开 zip 检查 XML 内容），改动前会先变红。

#### 导出失败了怎么查

分「生成」和「转发」两段，**提示不一样，看提示就能定位**：

生成段：

| 提示 | 含义 | 怎么办 |
|---|---|---|
| 「云函数执行超时」 | 云函数跑太久被平台掐掉。**函数没机会 return**，任何 message 都传不回来 | 生成已是毫秒级，正常不会出现。真遇到就查是不是数据量异常大，或在云开发控制台 → 云函数 → presence → 配置把**超时时间调大**（默认只有 3 秒） |
| 「导出失败：xxx」 | 函数内部真抛异常了，xxx 是原始错误 | 按 xxx 判断：数据库查询相关 → 集合/权限；上传相关 → 云存储权限 |
| 「仅管理员可导出」 | 你在 `staff` 里没有被标成管理员 | 名册管理 → 修改管理员标记 |

转发段：

| 提示 | 含义 | 怎么办 |
|---|---|---|
| 「当前环境不支持转发」 | `platform` 不是 `android` / `ios` | 用手机扫码「真机预览」后再点。文件已经生成好了，手机上重新点一次即可 |
| 「转发失败 / 原因：xxx」 | `shareFileMessage` 真的 fail 了，xxx 是**原始 errMsg** | 直接看 xxx：含 `TAP gesture` → 转发没落在点击手势里（回头查 `shareExport` 是否被加了 await）；含 `not supported` → 平台不支持；含 `file not exist` → 落地文件被清了，重新生成一次 |
| 用户自己点取消 | `errMsg` 含 `cancel` | **不弹任何提示**，这是正常操作 |

**为什么能这么分**：`exportAttendance` 套了 `try/catch`，把函数内部异常转成
`{success:false, message:'导出失败：' + 原始 message}` 回传——以前是直接往外抛，
云函数整体失败，前端只能显示笼统的「生成失败，请重试」，等于什么都没说。
**但超时兜不住**：平台直接终止进程，函数来不及 return，所以 `manage.js` 的 `doExport`
额外按 `errCode`（`-504003` / 错误信息含 timeout）把这种情况单独认出来，并给出改超时的指引。
两边配合，才让「三种挂法一个提示」变成可以自查的表格。

转发段的原始 `errMsg` 以前也被吞掉了——不管什么原因都只弹一句「转发未完成」，
和「生成失败，请重试」是同一个毛病。现在改成把 `errMsg` 原样放进弹窗，
哪怕看不懂也能截图定位。

### 「工作日」的判定：周末 + 法定节假日 + 调休

`date.js` 的 `isWorkday()` 不是简单的「周一到周五」，顺序是：

1. 在 `holidays.js` 的放假日表里 → **不是**工作日（中秋、国庆这些，含调休放假）；
2. 在 `holidays.js` 的调休上班表里 → **是**工作日（如 2026-10-10 周六要上班）；
3. 其余按周一~周五。

所以 3 / 7 个工作日两个视图遇到长假会自动跳过。例：9/23（周三）看到的是
`9/23 周三 · 9/24 周四 · 9/28 周一`——中间的中秋 9/25~9/27 不占列。
调休上班的周末会在列头日期下方挂一个「班」小标，避免周六排在列里看着像算错了。
「一个月」视图则相反：节假日不跳过，以**空心格**的形态留在月视图里，
这样「哪段时间是长假」在月视图里一眼就能看出来。

**月视图的四个状态色与色条必须取同一个色值**（`board.wxss` 的 `.mc-*` 与 `.bar-*`），
周末/节假日则刻意不用颜色——灰已经是「请假」的专属色，再拿一种灰表示休息日，
同屏两种灰会被读成同一个状态。所以休息日改成空心格（透明底 + 一圈淡描边），
连续的空心格就是一整段假期。

表头图例里有对应的一项「周末 / 法定节假日」（`board.wxml` 第 5 个 `.lg-item`）：

- 标记是 **方框** `.lg-sq`，不是前四项那种圆点 —— 形状不同才不会被读成第五种状态；
- 空心（只有描边、不填充），与格子是同一种形状语言；
- 描边色与 `.mc-rest` **逐字一致**，改一处必须改另一处（`presence-legend-test.js` 有断言守着）；
  线宽是 2rpx 而格子是 1rpx：格子的 1rpx 是 30 个挨在一起靠密度才看得出的，
  图例里只有一个孤零零的小方块，1rpx 在白底上几乎等于没有。

节假日数据在 `miniprogram/utils/holidays.js`，**国务院每年 10~11 月发布次年安排后需要人工补表**
（照抄通知里的放假区间，再加调休上班的日期，最后把新年份写进 `DATA_YEARS`）。
漏补的年份会走 `console.warn` 并按周一~周五兜底，不会整个看板不可用。

### 第二屏的色条必须先把「空档」补回来

这是踩过的一个坑，改这一块前务必先看懂。

服务端的 `mergeSegments()` 只会返回**有状态的那几段**，没有记录的空档是跳过的。
而前端的色条是 flex 布局（`flex-basis: 0`），宽度完全按各段的 `span` 比例分配——
所以如果只把「有状态的那几段」丢进去，剩下的色块会**被拉伸铺满整条**。

表现就是：上午京外出差（8:30-12:00，7 格）、下午没有任何记录，
`segments` 只有一个 `trip span:7`，色条全宽都是红的 —— 下午明明在岗。

修法：前端渲染前用 `utils/status.js` 的 `barsFromSegments(segments, '')` 补齐空档，
返回的分段**总长恒等于 19 格**，空档段的 `type` 为 `''`，由 `segClass()` 决定怎么上色
（已认领 → 在岗绿，未认领 → 空白色）。函数内部靠解析 `segments[].start/end` 的
`HH:MM` 文本还原格子下标，再用 `textToSlot()` 换算——所以**云函数那边不用改，也不用重新部署**。

「今天」那一屏没有这个问题：它是 19 个独立的点，空档在 `decorateRow()` 里已经直接映射成
`d-office`（绿点）了。

### 第二屏色条下方的不在岗文字（备注 + 时间段）

色条只说得清「哪半天不在岗」，说不清「去哪了 / 为什么」，所以第二屏在每根色条的正下方
列出当天所有**不在岗**时段：第一行备注（出差地 / 请假事由），第二行时间段。

- 一天有多段不在岗（上午病假、下午京内出差）就列多行，**可以同时显示多个**。
- **全在岗的那天不出文字**，行高不变——大部分人三天都全在岗，否则一屏看不了几个人。
- 在岗（`office`）永远不列：色条本身已经表达清楚了。
- 备注为空的老记录（备注是后加的必填项）退化成状态名（`京内` / `京外` / `请假`），
  否则色条下面会挂一行空白，看着像没加载出来。

**为什么备注和时间分两行**：单列只有约 183rpx
（`750 - 内边距 48 - 姓名列 128 - 两个 12rpx 间距`，再除以 3）。
28rpx 字号下「病假」占 56rpx、`08:30-12:00` 约 148rpx，拼成一行要 204rpx —— 放不下。
备注在 JS 里按 6 个汉字（12 个等效宽度，`NOTE_MAX_UNITS`）截断加省略号。

**每列要单独包一层 `.bar-cell`**：文字得跟自己的那根色条对齐，所以色条不能再自己 `flex: 1`，
改由 `.bar-cell` 占位（`.bar` 仍是 `display: flex`，负责条内分段）。

**数据来自服务端**：前端拿不到原始记录，所以 `rangeBoard()` 给每一天附加
`items: [{ type, time, note }]`，只含不在岗的段。备注匹配抽成了
`noteForSegment(mine, dateStr, seg)`，「今天」屏的标签和第二屏共用这一个函数：
**必须「类型相同 + 时间重叠」双重匹配**，否则同一天上午病假、下午包头两条记录
会把备注串到对方头上。跨天长记录按天切段后，每段都能匹配回同一条记录，
所以出差第二天仍然带同一个出差地。

⚠️ 这一项**需要重新部署 `presence` 云函数**（`items` 是新加的字段）。
前端对缺字段做了兼容（`(day.items || []).map(...)`），没部署时第二屏只是没有文字，不会报错。

### 时间段不做自动联动（改哪个字段就只改那个字段）

填写页的四个时间字段（开始日期 / 开始时刻 / 结束日期 / 结束时刻）**互不干预**。
唯一的例外是「连续 N 天」和三个快捷按钮——那是用户**主动点**的预设，本来就该一次填好四个。

早先这里有过一段联动，本意是省一步操作：

| 点选的去向 | 原来的联动 |
|---|---|
| 京外 / 请假 | 结束日期若还停在同一天 → 自动延到次日 |
| 京内 | 结束日期若跨天 → 收回同一天；结束时刻早于开始 → 再顺延 1 小时 |

**问题在于它会在用户已经填好日期之后突然改写**：先用「连续 5 天」把日期铺好，
再点一下「京内出差」，那 5 天会被硬缩成 1 天——看起来完全像出了 bug。
同理，`onStartDateChange` / `onEndDateChange` 里「日期顺序跟着对方挪」的逻辑也一并去掉了。

代价是用户现在能选出「结束早于开始」这类非法区间，所以补了两道：

- `refreshSpan()` 实时算出 `rangeWarnText`，在时间段卡片里标红提示（`.range-warn`）
- 点「保存」时仍然拦一次——**行内提示归提示，兜底不能少**

### 时间轴粒度固定 30 分钟，但录入不限

看板横轴 8:30 – 18:00 共 19 个格子，固定 30 分钟一格。

**录入则允许任意分钟**（原生时间选择器），因为出差往返往往不是整点。
两者不冲突：`buildDots()` 按「格子与记录区间**有交集**」点亮，
所以填 9:17 会点亮包含它的那一格，填 9:17–9:20 也会点亮整格——
这是有意的近似，宁可多显示一点，也不要让人「明明在岗却看不到」。

单条记录的起止跨度上限 **30 天**（前后端都做了校验），防止手滑选错月份。
超出 8:30 – 18:00 的安排可以保存，但看板时间轴不展示，填写页有说明文案。

### 快捷选项必须连日期一起写，不能只改时刻

最初的实现是「只改时刻、不动日期」，结果用户改过日期后点按钮毫无反应，以为按钮坏了。
现在每个快捷预设都会写全 `startDate / startTime / endDate / endTime` 四个字段。

预设统一以**今天**为锚点（所以标签里写明「今天上午」，而不是含糊的「上午」）。
标签和实际效果必须一致——写着「今天」却在别的日子里生效，比不给快捷键更让人困惑。

「连续 N 天」用步进器，点加减号立即生效，右侧显示算出来的日期范围，
点之前就知道会填成什么。当前区间恰好等于某个预设时那个按钮会高亮，
用户一眼看出「现在处于哪个预设」。

**两行「连续 N 天」：今天起 / 明天起。**

| 行 | 起点 | 天数范围 | 为什么下限不同 |
|---|---|---|---|
| 今天起连续 N 天 | 今天 08:30 | 2–30 天 | 1 天就是「今天整天」，上面已有现成按钮，不必重复 |
| 明天起连续 N 天 | 明天 08:30 | 1–30 天 | 1 天是「明天整天」，没有任何按钮能替代，必须允许 |

两行的天数**各自独立存放**（`days` / `daysTomorrow`），改一行不会影响另一行，
也没有任何跨行联动。这是刻意的——下面「时间段联动」那节记录过，
隐式联动（改 A 结果 B 跟着变）在这个项目里被明确否决过。

两行起点一个今天一个明天，区间不可能重合，所以任何时刻最多只有一行高亮。

`applyStreak(days, offset)` 的 `offset` 必须带默认值 `0`：漏传时
`addDays(t, undefined)` 会算出 Invalid Date，`startDate` 变成 `NaN`，
而区间校验只是静默失效、不报错，很难发现。

按钮放在时间选择器**下方**并标注「快捷选项（点一下自动填好）」——
放上面会让第一次用的人误以为是必填步骤。

### 「默认在岗」不写进数据库

没填的人在看板上直接显示为在岗，但这是**查询时临时补上的，不落库**。
一旦落库，就再也分不清谁是「真的在岗」、谁是系统补的，导出统计会失真。

界面上也不再区分这两者（都是实心绿点）：在岗本来就不需要填报，区分它没有意义。

判定顺序是：

1. 本人当天填过 → 用填的内容
2. 没填，但有跨天的出差/请假记录覆盖当天 → **延续那条**（出差的人不会第二天自动变在岗）
3. 都没有 → 按在岗显示（绿点）

第 2 步是自动的：记录存的是 `startAt` / `endAt` 时间戳，
查询条件是「与当天有交集」，所以跨天记录天然会被捞出来，不需要额外判断。

### 在办公室不可填报，但类型映射必须留着

填写页只提供**京内出差 / 京外出差 / 请假**三种选项——「在办公室」是默认状态，不填即在岗。

但 `utils/status.js` 的 `TYPES` 里**必须保留 `office`**：它是「类型 → 中文名 / 配色」的显示映射，
历史记录存过 `office`，删掉之后这些记录在看板上会没有颜色、在「我的记录」里会显示空白标签。

所以拆成两份：

| 用途 | 内容 |
|---|---|
| `TYPES` / `TYPE_MAP`（保留 4 种） | 显示映射，含 `office` |
| `PICK_TYPES`（3 种） | 填写页可选项，不含 `office` |

云函数里的 `VALID_TYPES` 同理保留 `office`，否则要修正历史数据时会被校验拦下。

因为没有了默认选项，提交时会校验「请先选择去向」——**不能让默认值代劳**，
否则一进页面直接点保存就会把在岗的人报成外出。

### 备注（出差地 / 请假事由）是必填的：请假只能点选、出差打字

备注栏的标题随去向变化，不是固定文案；**没选去向时整块备注卡不渲染**：

| 去向 | 标题 | 填写方式 | 占位文案 |
|---|---|---|---|
| 京内出差 / 京外出差 | 出差地（必填） | 打字（带历史点选） | 例如：市发改委、朝阳区、上海 |
| 请假 | 请假事由（必选） | **只能从 7 个固定选项里点选**，没有输入框 | —（输入框不渲染） |
| 未选去向 | —（整卡隐藏） | — | — |

标题随去向切换，所以 `noteMeta('')` 那套兜底文案正常交互下不会显示出来，
只是 data 初值不留 undefined 用。

**请假事由的 7 个固定选项**（`utils/note.js` 的 `LEAVE_REASONS`，未选请假时整块不渲染）：

> 事假 · 病假 · 年休假 · 探亲假 · 婚假 · 产假 · 丧假

- 为什么要固定：手打会写出「年假 / 年休假 / 公休」这类同义不同字，看板和统计里就无法归并了。
- **这是请假事由的完整取值域**：请假时输入框直接不渲染（`fill.wxml` 的 `wx:if="{{!isLeave}}"`），
  只能从这 7 项里选一个，**不能自己加文字**。
- 交互：点一下选中、**再点一下取消**；选中态是灰底白字，
  与上方「请假」去向按钮的选中态同一套色。没选就提交，提示「请选择请假事由」。
- 出差不设固定选项：出差地是地名，没有可选集合，输入框照常。
- 切换去向时会顺手清理不合法文案（`fill.js` 的 `onPickType`）：
  切到请假时，手打的出差地被清掉；切离请假时，原本选的「年休假」也被清掉
  ——否则会留下一个「改不掉又提交不了」的值。

其余口径：

- 文案集中在 `utils/note.js` 的 `noteMeta()`，前端标题、前端校验提示、云函数提示语都对齐它。
- 校验规则集中在 `utils/note.js` 的 `isValidNote(type, text)`：
  出差地非空即可、请假事由必须在 7 项白名单内。前端提交前走它。
- **前后端都拦，且请假多一道白名单**：云函数 `saveRecords` 除拒绝空备注外，
  还会拒绝不在 7 项内的请假事由（「请假事由请从选项中选择」），
  防止旧版本客户端或直接调接口写进自定义文字。
  云函数的 `LEAVE_REASONS` 常量必须与 `utils/note.js` 保持**逐字一致**，
  单测里有一条断言专门比对这两个常量。
- **历史记录只服务出差地**：`noteHistory()` 从「我的记录」里提取同类备注，
  去重、按最近使用排序、最多 8 条，点一下直接填入。
  **出差（京内 + 京外）合并成一组**（两者共用同一个「出差地」栏），
  请假**直接返回空**——事由已是固定选项，存量的自定义请假备注（「照料家人」之类）
  在新规则下根本填不回去，给出来就是一条走不通的路。
- 老记录里 note 大量为空（必填是后加的需求），提取时统一跳过，
  避免历史里混进一个点不动的空标签。

### 时区必须显式指定 +08:00

云函数运行在 UTC 时区。凡是把「北京时间的某天某刻」转成 `Date`，
都必须写成 `new Date('2026-09-14T08:30:00+08:00')`，漏掉 `+08:00` 就会整体偏移 8 小时，
「早上 8:30 上班」会被算成下午 16:30，整条时间轴全错。

读取时同理：不能直接用 `getHours()`（那拿到的是 UTC 小时），
要先整体 +8 小时再用 `getUTC*` 系列读取。见 `cloudfunctions/presence/index.js` 的 `beijingParts`。

### 100 人规模的两个约束

- 云数据库单次 `get()` **上限 100 条，超出会静默截断**（不报错，很隐蔽）。
  本项目按科室查询，并用 `skip + limit` 分页循环拉全。
- 100 人 × 19 个时间点 = 1900 个节点，一次渲染会卡。
  所以看板默认按科室筛选，且列表滚动时分批渲染（每批 24 人）。
